# Локальные иконки BitCraft: подключение к интерфейсу

Игровые WebP отображаются в рецептурной книге, справочнике ресурсов и пресетах добычи. Изображения входят в статический выпуск сайта. Автономная доступность зависит от кеша браузера.

Пакет игровых WebP относится к полному локальному набору. Публичный выпуск использует собственные иллюстрации по типам сущностей из [набора SVG](../web/icons/catalog.svg). Сборка и пути описаны в [инструкции по размещению](WEB_PORT.md#github-pages).

## Подключение в приложении

[Сборщик изображений](../scripts/build-entity-images.mjs) офлайн читает архивные `manifest.json` и `bindings.json`, проверяет snapshot и SHA-256, копирует доступные WebP в `web/assets/bitcraft/` и создаёт `web/data/entity-images.js`. Подготовьте набор командой `node scripts/build-entity-images.mjs` и проверьте его с `--check`. Затем пересоберите сайт.

Общий модуль [../web/entity-images.js](../web/entity-images.js) экспортирует `resolveEntityImage(entityOrKey, quantity)` и `entityImage(entityOrKey, options)`. Размеры контейнеров — `sm`, `md`, `lg`; изображение содержит пустой `alt`, потому что рядом обязательно есть название предмета. Для семейства используется доступный представитель, для Hex Coin — подходящий сохранённый вариант количества. При пустом пути, глифе, недоступном CDN-файле или ошибке чтения в том же контейнере показывается собственная иллюстрация. Тип определяется по английскому имени и категории из снимка. Тир задаёт оттенок металла инструментов и слитков.

`skillImageKey(id)` использует иконку подходящего предмета для навыков с глифами. В «Мире» иконки подбираются по связанному предмету, навыку, награде или цели разведки. Если значок цели отсутствует, можно показать связанный предмет запуска или биом. Прозрачный файл SilkenHexmoths сверяется по SHA-256 и пропускается при выборе значка.

## Фоновая загрузка в публичной сборке

Для подключения разрешённого источника создайте `data/public/remote-icons.json`. Формат ниже использует демонстрационный домен.

```json
{
  "baseUrl": "https://images.example.org/bitcraft/",
  "images": {
    "item:400827528": "items/antler.webp",
    "family:item:1606324183": "tools/pickaxe.webp"
  }
}
```

`baseUrl` — публичный HTTPS-адрес с завершающей косой чертой. `images` связывает ключи каталога с относительными путями внутри этого адреса. Для семейства подходит его ключ или связь с базовым предметом. Адреса из индекса доступны посетителям сайта.

После добавления файла пересоберите публичный выпуск командой `node scripts/build-web.mjs --public`. При размещении на GitHub Pages запустите существующий workflow публикации из `main`. Сборщик включает карту адресов и разрешает загрузку изображений с указанного домена. Файлы миниатюр хранятся у поставщика.

Сначала карточка рисует штатную SVG-иллюстрацию. При появлении карточки в области просмотра браузер запрашивает миниатюру и показывает её после загрузки. При ошибке или отсутствии сети остаётся SVG. Service worker сохраняет локальный набор иллюстраций, индекс и интерфейс. При отсутствии файла конфигурации сайт использует собственные иллюстрации.

Проверка `node tests/remote-images-ui.cjs` использует тестовый источник и проверяет отложенную загрузку, размеры карточки и работу при ошибке.

## Источник и версия

Ключи изображений взяты из сохранённых таблиц `data/bitcraft/raw/static/`. Их снимок — commit `af485cdbbb5cfaf9b6fd89742ecd7abac5009d3f` от `2026-11-13T14:34:19Z`; исходный манифест находится в `data/bitcraft/manifest.json`.

Изображения получены с `https://cdn.brico.app/sprites/`. Скачивание с CDN само по себе не подтверждает привязку каждого файла к commit таблиц: дата скачивания изображения и версия справочников — разные сведения. Происхождение и контрольные суммы записаны в манифесте пакета иконок. Это копии игровых ассетов, а не изображения, созданные для проекта.

Первичные правила адресации: [константы Cereal](https://github.com/BitCraftToolBox/cereal/blob/main/src/lib/constants.ts), [варианты SpriteImage](https://github.com/BitCraftToolBox/cereal/blob/main/src/components/SpriteImage.tsx), [getAssetURL Brico](https://github.com/BitCraftToolBox/brico/blob/main/frontend/src/lib/bitcraft-utils.ts).

## Где хранится пакет

```text
data/bitcraft/icons/
  manifest.json       источник, время скачивания и сведения о локальных файлах
  bindings.json       связи записей справочников с изображениями
  missing.json        отсутствующие и неподдержанные изображения
  files/
    <первые 2 символа хэша>/<хэш игрового пути>.webp
```

Одинаковый игровой путь скачивается один раз и может использоваться многими предметами, тирами и редкостями. Имя локального файла — SHA-256 **строки игрового пути**, а `sha256` в манифесте — контрольная сумма **содержимого файла**. Это разные значения.

Такой способ именования нужен для Windows: исходные пути могут различаться только регистром (`SeaGlass` / `Seaglass`, `ThumbsUp` / `Thumbsup`) и перезаписали бы друг друга в обычной папке. Не восстанавливайте локальный путь склейкой имени предмета или `icon_asset_name`; берите `file` из манифеста.

Обновление и проверка из корня проекта:

```powershell
python scripts/fetch-bitcraft-icons.py
node scripts/verify-bitcraft-icons.mjs
```

Для загрузчика нужен Python 3.10+ и доступ к источнику; для проверки — Node.js. Проверка выполняется на локальных файлах. Перед обновлением иконок после смены справочников сначала обновите и проверьте исходную выгрузку таблиц.

Обычный повторный запуск использует проверенные локальные файлы и сохранённые результаты 404/410. Для повторной проверки отсутствующих картинок выполните `python scripts/fetch-bitcraft-icons.py --retry-missing`; для полной загрузки заново — `python scripts/fetch-bitcraft-icons.py --refresh`. Параметр `--workers N` задаёт число параллельных загрузок от 1 до 8, по умолчанию 6; например, `--workers 4`. Сетевые ошибки со статусом `failed` при следующем запуске проверяются повторно.

## Как связать картинку с записью

Для обычной записи исходное поле `icon_asset_name` задаёт путь изображения. Например:

```text
resource_desc, id 1
  icon_asset_name = GeneratedIcons/Other/Sticks
  assetKey = GeneratedIcons/Other/Sticks
  локальный файл = manifest.assets[assetKey].file

building_desc, id 13 (Campfire)
  icon_asset_name = GeneratedIcons/Other/Buildings/Crafting/FireT1
  assetKey = GeneratedIcons/Other/Buildings/Crafting/FireT1
  локальный файл = manifest.assets[assetKey].file
```

Сначала найдите связь в `bindings.json`, затем возьмите указанный локальный файл. Пути `file` относятся к корню `data/bitcraft/icons/` (`bindings.pathBase` равно `.`). Не подставляйте CDN-адрес в `src` при ошибке: офлайн-приложение должно использовать локальную заглушку.

Различайте ключ исходной записи (`item_desc:1`, `cargo_desc:1`) и ключ сущности подготовленного каталога (`item:1`, `cargo:1`). Числовые ID разных справочников совпадают, поэтому общий словарь по одному числу недопустим.

### Поля индексов

| Файл и поле | Значение |
| --- | --- |
| `bindings.byEntity[entityKey]` | Ключ исходной записи, например `item:1` → `item_desc:1` |
| `bindings.records[recordKey]` | `table`, `idField`, `id`, `name`, исходное поле `field`, `sourceValue`, `kind`, `assetKey`, `variants`, `status`, `file` |
| `record.kind` | `image`, `glyph` или `empty` |
| `record.status` | `available`, `missing`, `failed`, `glyph` или `empty` |
| `record.variants[]` | Дополнительные варианты `{ minQuantity, assetKey }`; базовая картинка указана отдельно в `record.assetKey` |
| `manifest.assets[assetKey]` | Общие поля `status`, `file`, исходный `url`, `httpStatus`; у скачанного файла — `sha256`, `bytes`, `width`, `height`, `downloadedAt`; у ошибки — `checkedAt`, `error` |
| `asset.status` | `downloaded`, `missing` или `failed`; файл использовать только при `downloaded` |
| `missing.assets[]` | Недоступные файлы: отсутствуют на источнике или не скачались |
| `missing.records[]` | Записи без готовой картинки, включая глифы и пустые значения |

У некоторых справочников первичный ключ называется иначе, чем `id`; его имя сохранено в `idField`. При обработке исходных таблиц не предполагайте наличие `row.id` у каждой записи.

Минимальное разрешение базовой картинки после загрузки обоих JSON:

```js
const recordKey = bindings.byEntity[entity.key];
const record = bindings.records[recordKey];
const asset = record?.assetKey ? manifest.assets[record.assetKey] : null;
const relativeFile = asset?.status === 'downloaded' ? asset.file : null;
// relativeFile разрешается от локального корня пакета, а null — локальная заглушка.
```

В текущем `scripts/build-recipe-catalog.mjs` поле `icon_asset_name` не переносится в `web/data/recipe-catalog.json`. Приложение использует отдельный подготовленный индекс `web/data/entity-images.js` по ключу сущности; поле `iconPath` в каталог рецептов не добавляется.

Для `family:item:<id>` и `family:cargo:<id>` отдельного игрового ассета нет. Можно выбрать картинку представителя семейства через его `item:<id>` / `cargo:<id>`, сохранив остальные данные семейства. Рецепт тоже не является предметом: его иллюстрацию следует выбирать из результатов или требуемой станции, а не искать по числовому ID рецепта.

`building_requirement.building_type` у рецепта — тип станции, а не `building_desc.id`. Если нужна картинка конкретного станка, сначала разрешите требование в подходящее здание через функции и `building_function_type_mapping_desc`, затем используйте связь этого здания.

## Варианты количества: Hex Coin

Ключ `Items/HexCoin[,3,10,500]` обозначает несколько файлов, а не прямоугольники атласа и не анимационные кадры:

```text
assetKey: Items/HexCoin       → базовая картинка
assetKey: Items/HexCoin3      → вариант для количества 3
assetKey: Items/HexCoin10     → вариант для количества 10
assetKey: Items/HexCoin500    → вариант для количества 500
```

В квадратных скобках записаны пороги количества. Исходные CDN-файлы имеют соответствующие имена с `.webp`, локальные — хэшированные имена из `manifest.assets`. Не добавляйте `.webp` к полной строке со скобками: такой URL даёт 404.

Для обычной карточки достаточно `record.assetKey`. Если интерфейс показывает размер стопки, можно выбрать доступный вариант с наибольшим `minQuantity`, не превышающим количество; ниже первого порога использовать базовый. Это рекомендуемое правило нашего интерфейса, а не сохранённое поле игровой формулы. Проверяйте статус выбранного ассета и при его отсутствии возвращайтесь к доступной базовой картинке. Выбор изображения не меняет количество предметов в расчёте.

## Отсутствующие и особые значения

- Пустой путь означает, что в таблице иконка не задана. Это не ошибка скачивания.
- 404 означает, что указанный файл не найден на выбранном CDN на момент загрузки. Это не доказательство отсутствия ассета в самой игре.
- Значения вида `\uFFEA` в `skill_desc.icon_asset_name` являются кодами шрифтовых глифов, а не путями WebP. Их нужно подключать через соответствующий локальный шрифт или отдельное оформление интерфейса.
- `model_asset_name` обозначает модель, а не готовую иконку. Автоматически подменять им отсутствующий `icon_asset_name` нельзя.
- Для `tool_type_desc` иконка не задана отдельным полем: изображение конкретного инструмента можно получить через `tool_desc.item_id` и `item_desc`.

Полный список причин и затронутых записей сохраняется в `missing.json`. Состояние отсутствия изображения должно оставлять доступными название, характеристики и расчёт.

## Правила дальнейшей интеграции

1. Проверить пакет и выбрать нужные локальные файлы и индекс связей.
2. Разместить используемые файлы в обслуживаемом приложением каталоге, например `web/assets/bitcraft/`, и сохранить относительные пути `files/...`. Подготовленный индекс должен разрешать `file` от нового корня. Исходный пакет в `data/` остаётся архивом источников.
3. Создать небольшой модуль разрешения `entity.key → локальный URL`, общий для поиска, карточек, ингредиентов, результатов и станций. Преобразования путей не размазывать по HTML-шаблонам.
4. Сверстать изображение в контейнере постоянного размера с `object-fit: contain`; учитывать реальные размеры из манифеста. Название сущности должно читаться независимо от изображения.
5. Подключить локальную заглушку для пустой связи и ошибки чтения. Не запускать бесконечный цикл `onerror`, если заглушка тоже не загрузилась.
6. После изменения `web/` пересобрать сайт и проверить кеширование картинок.

Локальный сервер публикует содержимое `dist-web/`. Исходный пакет в `data/` предназначен для подготовки изображений. Интерфейс использует локальные пути внутри версионированного выпуска.

Перед правкой интерфейса прочитайте [UI_TARGET.md](UI_TARGET.md). Появление игровых картинок не меняет утверждённую тему «Лунная обсерватория».

## Проверка подключения

- Открыть предмет, ресурс, груз и станок с реально скачанными файлами.
- Проверить предмет без пути, запись с 404 и навык со шрифтовым глифом.
- Проверить совпадающий числовой ID у Item и Cargo и отдельную карточку семейства.
- Для Hex Coin проверить базовый файл и варианты количества, если они используются.
- Проверить длинное название, прозрачность и узкое окно. Полная локальная сборка использует изображения своего выпуска.
- После сборки проверьте кешированные изображения без сети. Файлы и манифест должны соответствовать одной локальной выгрузке.
